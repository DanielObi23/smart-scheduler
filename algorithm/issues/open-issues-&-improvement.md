2. Type: Input / AI
   Issue: the original idea (see `../../idea.md` and `../../rambling.md`) included an LLM layer — converting spoken/text input into structured tasks, and a chat interface for checking/adjusting the schedule conversationally. The LLM was never meant to touch the actual arranging logic (that stays fully deterministic/math-based), only the input and query surface around it. Decided not to build this.

3. Type: Scheduling
   Issue: in the split-task fallback (schedule.ts), slots are always consumed largest-first, regardless of which calendar day they fall on. When multiple candidate days tie on free-time size — which is common, since every day with no fixed commitments produces the same `Math.ceil(dailyCapacity + overflow)`-sized slot — the tie is broken by array order rather than by day. Because the flattened slot list is built in chronological order and JS's sort is stable, ties resolve to the furthest day sorting last, and the split loop consumes from the end of the list first. Net effect: a task that needs to split across several same-sized free days fills the furthest tied day before the soonest one, rather than front-loading into the nearest days first. Doesn't produce an incorrect schedule (total scheduled time is still correct, nothing double-books, the task still lands before its due date) — it's a suboptimal ordering, not a correctness bug. Fix would be a secondary sort key (day recency) alongside slot size when picking which slot to consume next.
